1.1 Compute & Machine Family 선택 기준 및 고대역폭 네트워킹

온프레미스 x86 서버나 타 클라우드의 인스턴스 패밀리를 운영하던 엔지니어가 Google Compute Engine을 설계할 때 가장 먼저 정립해야 할 기준은 세대별 하드웨어 오프로딩 아키텍처(Titanium), 네트워크 인터페이스 드라이버(gVNIC), 그리고 호스트 유지보수 시의 Live Migration 동작입니다.

머신 시리즈 프로세서 및 아키텍처 기반 지원 스토리지 유형 네트워크 드라이버 / 최대 대역폭 적합한 엔터프라이즈 워크로드
E2 환경에 따른 동적 CPU 할당 (Intel / AMD) Persistent Disk virtio-net 또는 gVNIC / 최대 16Gbps 개발/테스트 환경, 트래픽 변동이 적은 경량 백오피스 및 배치
N2 / N2D Intel Ice Lake / AMD EPYC Milan Persistent Disk, Hyperdisk virtio-net, gVNIC / Tier 1 시 최대 100Gbps 표준 엔터프라이즈 웹/WAS, 일반 마이크로서비스 클러스터
N4 Intel Emerald Rapids + Titanium 오프로딩 Hyperdisk 전용 (Hyperdisk Balanced 기본) gVNIC 필수 / 최대 50Gbps 높은 가격 대비 성능과 균일한 I/O 응답 시간이 요구되는 차세대 표준 API 서버
C3 / C3D / C4 Intel Sapphire/Emerald Rapids, AMD Genoa + Titanium IPU Hyperdisk 중심 (Local SSD 옵션 제공) gVNIC 필수 / Tier 1 시 최대 200Gbps 초저지연 코어 트랜잭션, 암호화/패킷 처리, 고성능 API 게이트웨이 및 DB 엔진
Titanium 아키텍처와 gVNIC 필수화
  • Titanium IPU 하드웨어 오프로딩: 3세대 이후 머신(N4, C3, C4)은 네트워크 가상화(Andromeda SDN 패킷 처리)와 스토리지 암호화/I/O 연산을 호스트 CPU에서 분리하여 전용 하드웨어인 Titanium 어댑터에서 처리합니다. 이를 통해 이웃 VM으로 인한 성능 간섭(Noisy Neighbor)을 방지하고 일관된 클럭 성능을 제공합니다.
  • gVNIC (Google Virtual NIC): 3세대 이상 VM에서는 레거시 virtio-net 드라이버가 지원되지 않으며, gVNIC 드라이버가 포함된 OS 이미지를 사용해야 합니다.
  • vCPU당 이그레스 대역폭 상한 주의: 기본 네트워크 구성을 사용할 경우 VM의 아웃바운드 대역폭은 vCPU 코어당 2Gbps(머신 타입별 기본 상한 32~50Gbps)로 제한됩니다. 대용량 트래픽을 중계하는 프록시나 미디어/데이터 노드는 반드시 gVNIC과 함께 Tier 1 네트워킹 옵션을 활성화하여 최대 100~200Gbps 대역폭을 확보해야 합니다.
호스트 유지보수: Live Migration vs Terminate
  • Live Migration 기본 동작: 물리 서버 펌웨어 패치나 하드웨어 예방 점검 시, 일반 GCE VM은 재부팅 없이 실행 중인 메모리 페이지와 활성 TCP 세션을 유지한 채 인접 물리 호스트로 이동합니다.
  • 클러스터 하트비트 튜닝 포인트: Live Migration 최종 전환 순간에 수십~수백 밀리초 수준의 짧은 프리징(Blackout window)이 발생할 수 있습니다. 온프레미스용으로 설계된 자체 HA 솔루션이나 BFD에서 하트비트 타임아웃을 1초 미만으로 극단적으로 짧게 설정하면 오탐 페일오버가 발생할 수 있으므로 최소 3~5초 이상으로 설정하는 것이 안전합니다.
  • Terminate 대상 인스턴스 대응: GPU 인스턴스, 대용량 Local SSD 장착 VM, 베어메탈 인스턴스는 Live Migration이 불가하여 TERMINATE 정책이 적용됩니다. 이 경우 메타데이터 서버의 maintenance-event 속성을 주기적으로 폴링하여 사전 드레이닝을 수행해야 합니다.
Bash · 호스트 유지보수 이벤트(maintenance-event) 실시간 감지 스크립트 예시 
#!/usr/bin/env bash
# 메타데이터 서버에서 호스트 유지보수 예고(MIGRATE_ON_HOST_MAINTENANCE 또는 TERMINATE_ON_HOST_MAINTENANCE) 감지
EVENT=$(curl -s -H "Metadata-Flavor: Google" \
  "http://metadata.google.internal/computeMetadata/v1/instance/maintenance-event")

if [ "$EVENT" != "NONE" ]; then
  logger -t gce-maintenance "Host maintenance event detected: ${EVENT}. Starting graceful drain..."
  # 로컬 헬스체크 상태를 Unready로 전환하여 로드 밸런서 신규 유입 차단
  touch /tmp/unready
fi

1.2 Storage & Image 엔지니어링: Hyperdisk와 Golden Image 파이프라인

스토리지 설계에서 가장 중요한 변화는 디스크 크기(GB)와 성능(IOPS/Throughput)의 결합을 해체한 Hyperdisk의 도입이며, 프로비저닝 속도 및 안정성 측면에서는 부팅 시 패키지 설치를 배제한 Golden Image 파이프라인 구축이 핵심입니다.

비교 항목 Persistent Disk (pd-balanced, pd-ssd) Google Cloud Hyperdisk (hyperdisk-balanced, hyperdisk-extreme)
성능 결정 구조 디스크 할당 용량(GB) 및 VM vCPU 수에 비례하여 IOPS와 처리량이 선형적으로 고정됨 용량(GB)과 성능(IOPS, MB/s)이 완전히 분리됨 (소용량 디스크에도 고성능 IOPS 독립 할당 가능)
비용 효율성 높은 IOPS를 얻기 위해 실제로는 쓰지 않는 수 TB의 디스크 용량을 과다 할당해야 하는 비용 낭비 발생 필요한 용량(예: 100GB)만 할당하고 원하는 IOPS(예: 20,000 IOPS)와 처리량만 정밀하게 프로비저닝 가능
운영 중 성능 변경 성능을 높이려면 디스크 크기를 영구 증설해야 함 (축소 불가) VM 무중단 상태에서 API / CLI / Terraform으로 IOPS 및 처리량 수치를 동적으로 상향 및 하향 조정 가능
스토리지 풀 공유 개별 디스크 단위로만 프로비저닝 Hyperdisk Storage Pools를 통해 여러 VM이 사전 확보된 용량과 IOPS 풀을 씬 프로비저닝으로 공유 가능

2.1 UMIG vs MIG 아키텍처 및 Regional MIG 멀티존 분산 알고리즘

Compute Engine의 인스턴스 그룹은 비관리형(UMIG)과 관리형(MIG)으로 나뉩니다. 프로덕션 환경에서는 단일 존 장애(Zone Outage) 시에도 서비스 연속성을 보장하기 위해 단일 서브넷 위에서 3개 존에 걸쳐 동작하는 Regional MIG를 기본 아키텍처로 채택합니다.

비교 항목 Unmanaged Instance Group (UMIG) Zonal MIG Regional MIG (엔터프라이즈 표준)
구성 방식 수동 생성된 이기종 VM들을 임의로 묶은 그룹 단일 존 내부에 동일한 Instance Template으로 배포 리전 내 복수 존(기본 3개 존)에 걸쳐 동일한 Instance Template으로 자동 분산 배포
자동화 기능 Autoscaling, Autohealing, Rolling Update 전부 미지원 Autoscaling, Autohealing, Rolling/Canary Update 지원 Autoscaling, Autohealing, Rolling/Canary Update + 존 간 자동 분산 및 장애 격리 지원
권장 사용처 레거시 리프트 앤 시프트 과도기 외에는 사용 지양 특정 존에 고정된 단일 데이터베이스와의 초저지연 통신이 필수인 특수 배치 워크로드 모든 무상태(Stateless) 웹/WAS, API 서버, 프록시 계층 및 고가용성 클러스터

Regional MIG의 Target Distribution Shape 3가지 모드

1. EVEN 모드

리전 내 선택된 모든 존에 인스턴스 대수를 정확히 동일하게 유지합니다. 특정 존에 일시적인 하드웨어 용량 부족이 발생하더라도 타 존에 대체 생성하지 않고 해당 존 할당량을 고수합니다. 존별 예약이 100% 확보된 환경에 적합합니다.

2. BALANCED 모드

기본적으로 존 간 균등 배치를 유지하지만, 특정 존에 장애나 용량 부족이 발생하면 가용한 다른 존에 인스턴스를 우선 프로비저닝하여 전체 목표 대수(Target Size)를 지키는 데 최우선 순위를 둡니다. 미션 크리티컬 서비스에 가장 권장되는 설정입니다.

3. ANY / ANY_SINGLE_ZONE

존 간 균등성보다 가용 용량 확보나 Spot VM 활용, 특정 존의 미사용 예약 리소스 소진을 우선시합니다. 대규모 배치 처리나 단일 존 몰아주기(지연 시간 최소화)가 필요한 워크로드에 사용합니다.

Proactive Redistribution (선제적 재분배) 제어 팁: 존 간 인스턴스 수 불균형이 해소되었을 때 MIG가 자동으로 다른 존의 VM을 삭제하고 원래 존으로 재배치하여 균형을 맞추는 기능입니다. 무상태 웹 서버에는 유용하지만, 부팅 후 로컬 인메모리 캐시 워밍에 시간이 오래 걸리는 서비스나 Stateful MIG에서는 불필요한 재시작을 유발하므로 --instance-redistribution-type=NONE으로 비활성화해야 합니다.

2.2 무중단 배포 메커니즘과 Rolling 및 Canary 필수 파라미터

Instance Template은 한 번 생성하면 수정할 수 없는 불변(Immutable) 리소스입니다. 애플리케이션 버전이나 커널 설정을 변경하려면 신규 템플릿(v2)을 생성한 뒤 MIG의 updatePolicy를 통해 무중단 교체를 수행합니다.

Architecture · Regional MIG 무중단 Rolling Update 및 단일 MIG Canary 배포 흐름 
[단일 Regional MIG 내 Canary 배포 (다중 템플릿 버전 분할)]
  ├── versions[0] (Primary): instance-template-v1 (90% 트래픽 처리)
  └── versions[1] (Canary) : instance-template-v2 (targetSize: fixed=1 또는 percent=10%)
  * 별도의 카나리용 MIG를 추가 생성하거나 LB 설정을 건드릴 필요 없이 단일 MIG 내부에서 카나리 검증 완료!

[검증 완료 후 100% 무중단 Rolling Update (type = PROACTIVE, replacementMethod = SUBSTITUTE)]
  1. maxSurge=3 (존당 1대씩 신규 v2 VM 3대 선제 프로비저닝, 기존 v1 VM은 100% 정상 가동 유지)
  2. v2 VM 부팅 완료 → Load Balancer Health Check HEALTHY 판정
  3. minReadySec=60 (헬스체크 통과 후에도 JVM/애플리케이션 캐시 워밍업을 위해 60초간 추가 대기)
  4. maxUnavailable=0 원칙에 따라, 신규 v2 VM이 완전히 준비된 후에만 기존 v1 VM의 Connection Draining 시작
업데이트 파라미터 권장 프로덕션 설정값 내부 동작 원리 및 설계 주의사항
type PROACTIVE 템플릿 변경 즉시 롤링 교체를 시작합니다. (반면 OPPORTUNISTIC은 즉시 교체하지 않고 추후 스케일아웃이나 Autohealing으로 새 VM이 생성될 때만 새 템플릿을 적용하므로 피크 타임 중 변경 사항만 먼저 반영해 둘 때 유용합니다.)
replacementMethod SUBSTITUTE 새 이름을 가진 신규 VM을 먼저 생성하여 트래픽을 넘긴 뒤 구버전 VM을 삭제합니다. (RECREATE는 기존 VM을 먼저 종료하고 동일 이름으로 다시 생성하므로 maxSurge=0이 강제되며 다운타임이나 용량 감소가 발생합니다.)
maxUnavailable 0 (필수) 업데이트 도중 목표 대수 대비 감소해도 되는 인스턴스 수입니다. 무중단 배포를 위해서는 반드시 0으로 설정하여 신규 인스턴스가 완전히 준비되기 전에는 기존 인스턴스가 절대 내려가지 않도록 강제해야 합니다.
maxSurge 3 이상 (또는 20%) 업데이트 중 목표 대수를 초과해 임시로 더 생성할 수 있는 인스턴스 수입니다. 3개 존을 사용하는 Regional MIG에서는 최소 3 이상으로 설정해야 3개 존에서 동시에 병렬 교체가 진행되어 배포 속도가 빨라집니다.
minReadySec 30 ~ 120초 신규 VM이 부팅되고 헬스체크가 HEALTHY로 통과한 직후에도, 다음 배치 교체를 진행하기 전에 추가로 대기할 워밍업 시간(초)입니다.

2.3 Autoscaling 제어 및 Health Check 이원화 아키텍처

엔터프라이즈 핵심 원칙 (연쇄 장애 방지): Load Balancer Health Check(Readiness)와 MIG Autohealing Health Check(Liveness)에 동일한 헬스체크 리소스나 동일한 엔드포인트를 공유해서는 안 됩니다. 만약 두 헬스체크가 모두 백엔드 데이터베이스 연결 상태를 검사하도록 묶여 있으면, DB에 10초짜리 일시적 순단이나 슬로우 쿼리가 발생했을 때 LB가 트래픽을 잠시 차단하는 데 그치지 않고 MIG Autohealer가 전체 WAS 인스턴스를 고장 난 것으로 오판하여 동시에 강제 삭제 및 재설치하는 대형 연쇄 장애(Cascading Failure)가 발생합니다.
구분 Load Balancer Health Check (Readiness 역할) Autohealing Health Check (Liveness 역할)
검증 목적 이 인스턴스가 지금 당장 클라이언트 요청을 정상 처리할 수 있는가? 이 인스턴스의 데몬이나 OS가 완전히 데드락/크래시되어 VM 자체를 폐기하고 새로 찍어내야 하는가?
실패 시 시스템 동작 Load Balancer의 라우팅 풀에서만 즉시 제외됨 (VM은 삭제되지 않고 유지되며, 헬스체크가 다시 성공하면 즉시 트래픽 재투입) MIG가 해당 VM을 강제 삭제(Delete)하고 신규 VM을 처음부터 다시 프로비저닝 (복구에 최소 수 분 소요)
권장 엔드포인트 설계 /healthz/ready (로컬 캐시 준비 상태, 다운스트림 의존성 상태 및 Graceful Shutdown 시 의도적 503 반환 포함) /healthz/live (외부 DB나 타 API 의존성을 배제하고, 오직 로컬 웹/WAS 프로세스 자체의 생존 여부만 가볍게 확인)
권장 주기와 임계치 민감하게 설정: 주기 5초, 타임아웃 3초, 연속 실패 2회 (10초 내 장애 노드 트래픽 격리) 보수적으로 설정: 주기 10~15초, 타임아웃 5초, 연속 실패 3~5회 (30~75초 이상 완전 불능 시에만 재구축) + initialDelaySec=300

Autoscaling Scale-in Control 및 Graceful Shutdown

트래픽 피크가 끝난 직후 Autoscaler가 인스턴스를 급격하게 축소(Scale-in)하면, 남은 인스턴스의 로컬 캐시 미스가 급증하거나 짧은 시간 뒤 다시 찾아온 2차 트래픽 스파이크에 대응하지 못합니다. 이를 방지하기 위해 scaleInControl을 설정하여 일정 시간 동안 줄어들 수 있는 최대 인스턴스 수 또는 비율을 제한합니다.

Terraform HCL · 다중 지표 Autoscaling 및 Scale-in Control 구성 예시 
resource "google_compute_region_autoscaler" "was_autoscaler" {
  name   = "prod-was-autoscaler"
  region = "asia-northeast3"
  target = google_compute_region_instance_group_manager.was_rmig.id

  autoscaling_policy {
    min_replicas    = 6
    max_replicas    = 30
    cooldown_period = 90

    cpu_utilization {
      target            = 0.65
      predictive_method = "OPTIMIZE_AVAILABILITY"
    }

    # 급격한 축소 방지: 최근 10분(600초) 동안 피크 대수 대비 최대 20%까지만 축소 허용
    scale_in_control {
      time_window_sec = 600
      max_scaled_in_replicas {
        percent = 20
      }
    }
  }
}

2.4 Stateful MIG 아키텍처와 3대 구조적 한계

레거시 금융 솔루션, 라이선스가 호스트명/IP에 귀속되는 상용 소프트웨어, 또는 카프카/엘라스틱서치처럼 개별 노드의 고유 디스크와 식별자가 유지되어야 하는 워크로드를 위해 MIG는 Stateful Policy와 Per-instance Configuration(인스턴스별 개별 구성)을 제공합니다.

Stateful MIG가 보존하는 4가지 상태
  • 인스턴스 이름 보존: 재생성 후에도 동일한 VM 이름 유지
  • 영구 디스크(PD/Hyperdisk) 보존: VM이 Autohealing으로 삭제 후 재생성되더라도 기존 부팅/데이터 디스크를 지우지 않고 새 VM에 그대로 재마운트 (autoDelete=false 자동 관리)
  • 내부 및 외부 고정 IP 보존: 장애 복구 시에도 동일한 사설/공인 IP 주소 재할당
  • 인스턴스별 고유 메타데이터 보존: node_id=broker-01 등 개별 노드의 설정값 유지
도입 전 반드시 알아야 할 3대 구조적 제약사항
  • 1. Autoscaling 동시 사용 불가: 각 인스턴스가 고유한 상태와 디스크를 가지므로 자동 수평 확장(Autoscaling)을 활성화할 수 없습니다.
  • 2. 교차 존(Cross-Zone) 자동 페일오버 미지원: Stateful MIG의 Autohealing은 장애가 발생한 바로 그 존(Zone) 내부에서만 VM을 재생성하고 Zonal 디스크를 재부착합니다. 특정 존 전체 장애 시 타 존으로 자동 이동하지 않습니다.
  • 3. 롤링 업데이트 시 RECREATE 강제: 동일한 이름, IP, 디스크를 새 VM에 다시 물려야 하므로 기존 VM을 먼저 내렸다가 올리는 RECREATE 방식만 사용할 수 있습니다.
운영자 필수 주의사항 (Compute Engine VM API vs MIG API): MIG에 속한 인스턴스를 점검하거나 교체할 때 gcloud compute instances delete(단일 VM API)로 직접 삭제하면, MIG 컨트롤러는 이를 "예기치 않은 장애로 인한 인스턴스 유실"로 판단하여 즉시 동일한 VM을 다시 생성합니다. 특정 인스턴스를 그룹에서 제거하거나 재구축할 때는 반드시 gcloud compute instance-groups managed delete-instances 또는 recreate-instances(MIG API)를 호출해야 합니다.

3.2 Proxy LB vs Passthrough LB 패킷 흐름 및 Direct Server Return 원리

네트워크 운영팀이 방화벽 정책, tcpdump 패킷 분석, 클라이언트 원천 IP 보존 아키텍처를 설계할 때 가장 명확히 구분해야 하는 두 가지 데이터 플레인 동작 방식입니다.

비교 항목 Proxy Load Balancer (L7 ALB, L4 Proxy NLB) Passthrough Load Balancer (External/Internal Passthrough NLB)
TCP / TLS 세션 종료 LB(GFE/Envoy)에서 클라이언트의 TCP/TLS 세션을 완전히 종료하고, 백엔드 VM과 별도의 새로운 TCP 연결을 수립함 LB는 세션을 종료하지 않고 클라이언트가 보낸 원본 패킷(IP/Port 헤더 변조 없음)을 그대로 백엔드 VM에 전달함
백엔드가 보는 Source IP Google 프록시/헬스체크 대역 (35.191.0.0/16, 130.211.0.0/22) 또는 VPC 내 Proxy-only Subnet 대역 클라이언트의 실제 원본 Source IP가 L3 헤더에 그대로 보존됨
클라이언트 원천 IP 확인 L7은 HTTP X-Forwarded-For 헤더, L4 Proxy는 PROXY protocol v1/v2 헤더를 파싱하여 확인 별도 헤더 파싱 없이 소켓의 L3 Source IP에서 직접 확인
백엔드가 보는 Destination IP 백엔드 VM 자신의 Private NIC IP (예: 10.10.0.15) Load Balancer(Forwarding Rule)의 VIP (예: 10.10.0.99 또는 공인 VIP)
응답 패킷 경로 백엔드 VM → LB 프록시 → 클라이언트 (대칭 경로) Direct Server Return (DSR): 백엔드 VM이 LB를 거치지 않고 클라이언트에게 직접 응답 패킷 전송

심화 해부: Passthrough LB에서 왜 백엔드 VM은 자기 NIC IP가 아닌 LB VIP 패킷을 드롭하지 않는가?

패스스루 로드 밸런서는 목적지 IP(Destination IP)를 백엔드 VM의 사설 IP로 변환(DNAT)하지 않고, Forwarding Rule의 VIP가 찍힌 상태 그대로 백엔드 호스트에 전달합니다. 일반적인 리눅스 커널이라면 자신의 네트워크 인터페이스 IP가 아닌 패킷을 수신했을 때 이를 즉시 폐기(Drop)해야 정상입니다. GCE에서 이 패킷이 정상 수신되고 DSR 응답이 나가는 원리는 다음과 같습니다:

  • 1단계 (Andromeda 캡슐화 전달): Maglev 또는 Andromeda 가상 스위치는 안쪽 패킷의 L3/L4 헤더(Src: 클라이언트 IP, Dst: LB VIP)를 전혀 수정하지 않은 채, 바깥쪽에 Andromeda SDN 터널 헤더만 씌워 타겟 백엔드 VM이 실행 중인 물리 호스트로 전달합니다.
  • 2단계 (google-guest-agent의 로컬 라우트 자동 주입): GCE 표준 OS 이미지 내부에서 실행되는 google-guest-agent 데몬이 메타데이터 서버를 상시 감시하다가, 해당 VM이 Passthrough LB의 백엔드로 등록되면 리눅스 커널의 local 라우팅 테이블에 LB VIP를 프로토콜 식별자 proto 66으로 자동 등록합니다.
  • 3단계 (로컬 소켓 수신 및 DSR 직접 응답): 커널의 local 테이블에 LB VIP가 등록되어 있으므로 리눅스 커널은 해당 패킷을 자기 자신에게 온 패킷으로 인식하여 애플리케이션 소켓으로 전달합니다. 응답 패킷을 보낼 때도 출발지 IP를 LB VIP로 달아서 클라이언트로 직접 반환(Direct Server Return)합니다.

1. 하이브리드 연동 시 Global Access

Dedicated Interconnect나 HA VPN 너머의 온프레미스 데이터센터 서버에서 GCP 내부의 Internal ALB/NLB VIP를 호출하려면, Internal Forwarding Rule에 반드시 --allow-global-access 플래그를 활성화해야 합니다. 기본값은 동일 리전 내 클라이언트로만 제한됩니다.

2. Internal NLB Next-hop 방화벽

서드파티 보안 장비(Palo Alto, Fortinet 등 NVA)를 MIG로 구성한 뒤 앞단에 Internal Passthrough NLB를 배치하고, VPC 라우팅 테이블의 Next-hop(--next-hop-ilb)으로 지정하면 BGP 수렴 지연 없는 무중단 인라인 보안 구간과 대칭 해싱(Symmetric Hashing)을 구현할 수 있습니다.

3. Cloud NAT 포트 고갈 방지

Private VM이 외부 단일 목적지(예: 외부 결제/오픈뱅킹 API VIP:443)로 동시 다발적인 연결을 맺을 때 기본 정적 포트(64개)는 즉시 고갈(OUT_OF_RESOURCES)됩니다. 반드시 Dynamic Port Allocation(minPortsPerVm=256~1024, maxPortsPerVm=65536)을 켜고 복수의 공인 NAT IP를 할당해야 합니다.

3.4 LB + MIG 연동 실전 운영: Balancing Mode와 Keep-alive 502 방지 공식

1. Balancing Mode 선택 기준: UTILIZATION vs RATE vs CONNECTION

Balancing Mode 적용 가능 LB 동작 특징 및 프로덕션 설계 가이드
UTILIZATION L7 ALB, L4 Proxy 백엔드 MIG의 CPU 사용률을 기준으로 트래픽을 배분합니다. 단, 백엔드 애플리케이션이 DB 쿼리나 외부 API 응답 대기로 인해 CPU 사용률은 10%인데 워커 스레드 풀이 고갈된 경우(I/O Bound), LB는 여유가 있다고 판단해 계속 트래픽을 밀어넣어 장애를 확대시킬 수 있습니다.
RATE (권장) L7 ALB 전용 인스턴스당 초당 최대 HTTP 요청 수(maxRatePerInstance)를 기준으로 제어합니다. L7 ALB와 MIG 연동 시 가장 예측 가능하고 안전한 모드입니다. 주의할 점은 maxRatePerInstance를 MIG Autoscaler의 목표치보다 1.5~2배 여유 있게 설정하여, 스케일아웃이 완료되기 전에 LB가 트래픽을 과도하게 드롭(503)하거나 타 존으로 스필오버시키지 않도록 설계해야 합니다.
CONNECTION L4 Proxy / Passthrough NLB 동시 활성 TCP 연결 수를 기준으로 트래픽을 분배합니다.

2. LB-Backend 간 Keep-alive 타임아웃 미스매치와 502 Bad Gateway 방지 황금 공식

프로덕션 환경에서 간헐적으로 발생하는 502 Bad Gateway 에러의 90% 이상은 로드 밸런서와 백엔드 웹/WAS 서버 간의 HTTP Keep-alive 유휴 타임아웃(Idle Timeout) 불일치로 인한 TCP Race Condition 때문에 발생합니다.

네트워크 병목 vs 백엔드 애플리케이션 병목 3초 판별법

간헐적인 응답 지연이 발생했을 때 Cloud Load Balancing 로그의 두 가지 지연 시간 필드를 비교하면 원인이 네트워크/클라이언트 구간인지 백엔드 서버 구간인지 즉시 판별할 수 있습니다:

httpRequest.latency: 전체 왕복 지연 시간

클라이언트가 보낸 요청의 첫 번째 바이트가 Google LB(GFE/Envoy)에 도착한 순간부터, LB가 클라이언트에게 응답의 마지막 바이트를 전송 완료할 때까지 걸린 전체 왕복 처리 시간(total_latencies)입니다.

jsonPayload.backend_target_latency: 순수 백엔드 처리 시간

LB 프록시가 백엔드 MIG VM으로 요청을 전달하기 시작한 시점부터 백엔드 VM으로부터 응답을 모두 수신할 때까지 걸린 순수 백엔드 처리 시간(backend_latencies)입니다.

  • 케이스 A (total_latencies = 3.05s, backend_latencies = 3.01s): 100% 백엔드 WAS 애플리케이션 또는 뒷단 DB 슬로우 쿼리 병목입니다.
  • 케이스 B (total_latencies = 3.20s, backend_latencies = 0.04s): 백엔드 VM은 40ms 만에 응답을 마쳤으나, 클라이언트의 무선 네트워크 품질 저하로 대용량 응답 페이로드 수신이 지연되었거나 클라이언트의 요청 본문 업로드 자체가 느렸던 케이스입니다.

response_sent_by_backend 2xx ~ 5xx LB 및 네트워크 구간 이상 없음. 백엔드 서버가 직접 생성하여 반환한 HTTP 응답 코드입니다 (백엔드 애플리케이션 자체가 500/502/504를 반환한 경우 포함).

4.3 아키텍처 & 실무 운영 핵심 Q&A

Q1. 타 클라우드에서는 서브넷을 가용 영역마다 쪼개서 만들고 라우팅 테이블도 Public/Private으로 분리하는데, GCP에서는 왜 리전당 서브넷 하나만 만드나요?

GCP VPC의 서브넷은 특정 존에 묶이지 않는 리전(Regional) 리소스입니다. 또한 GCP에는 물리적인 인터넷 게이트웨이 객체가 별도로 존재하는 것이 아니라 기본 라우트(0.0.0.0/0 → default-internet-gateway)가 논리적으로 존재하며, VM에 외부 IP가 부여되어 있거나 해당 서브넷에 Cloud NAT가 연결되어 있을 때만 인터넷 아웃바운드 통신이 작동합니다. 따라서 존마다 서브넷 CIDR을 쪼갤 필요가 없어 IP 대역 단편화가 사라지고, Regional MIG가 3개 존에 걸쳐 유연하게 스케일링할 수 있습니다.

Q2. 온프레미스 방화벽에서 GCP 앞단의 L7 Application Load Balancer IP를 목적지로 허용해야 하는데, ALB의 IP가 바뀌지는 않나요?

바뀌지 않습니다. Global External ALB나 Regional External ALB의 Forwarding Rule에 예약된 고정 외부 IP(Static External IP)를 바인딩하면 해당 Anycast 또는 Regional VIP는 영구적으로 고정됩니다. 하이브리드 전용선으로 연동되는 Internal ALB 역시 지정한 서브넷 내의 특정 고정 사설 IP를 영구 할당할 수 있습니다.

Q3. 쿠버네티스를 도입하지 않고 GCE VM과 MIG 기반으로만 서비스를 운영할 때도 정교한 카나리 배포와 무중단 롤백을 구현할 수 있나요?

충분히 가능합니다. 단일 Regional MIG의 다중 템플릿 버전 기능(--version + --canary-version)을 사용하여 인스턴스 대수 비율로 카나리를 수행하거나, Envoy 기반 L7 ALB(EXTERNAL_MANAGED / INTERNAL_MANAGED)의 URL Map에서 두 개의 MIG Backend Service 간 가중치 기반 트래픽 스플리팅(Weight-based Traffic Splitting, 예: 95:5)을 설정하면 GKE나 서비스 메시 없이도 요청 단위 비율 제어와 1초 만의 즉시 롤백을 수행할 수 있습니다.
