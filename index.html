Session 1 GCE 코어 아키텍처 및 엔터프라이즈 구축 가이드

1. 워크로드 특성별 머신 시리즈 및 gVNIC 네트워킹

머신 패밀리 및 Titanium 아키텍처
  • N2 / N2D / N4: 표준 웹/WAS 및 마이크로서비스 워크로드용 범용 시리즈입니다. N4 시리즈는 Titanium 오프로딩 아키텍처와 Hyperdisk Balanced를 기본 탑재하여 가격 대비 균일한 성능을 제공합니다.
  • C3 / C3D / C4: 저지연 트랜잭션, 암호화/패킷 처리, 고성능 연산 워크로드에 사용합니다. 네트워크 및 스토리지 I/O 가상화 처리를 전용 하드웨어인 Titanium IPU로 오프로딩하여 호스트 CPU 간섭을 제거합니다.
  • Live Migration vs Terminate: 일반 GCE VM은 물리 호스트 점검 시 메모리와 TCP 세션을 유지한 채 다른 호스트로 이동하는 Live Migration을 기본 수행합니다. Local SSD 대량 장착이나 GPU 인스턴스처럼 `TERMINATE`가 적용되는 스펙은 메타데이터 서버의 `maintenance-event` 속성을 감시해 사전 드레이닝을 구성합니다.
gVNIC 드라이버 및 Persistent Disk vs Hyperdisk
  • gVNIC 및 Tier 1 대역폭: 3세대 이후 머신(N4, C3, C4)은 `virtio-net` 대신 Google Virtual NIC(`gVNIC`) 사용이 필수입니다. Andromeda SDN과 직접 결합되어 인터럽트 오버헤드를 줄이고 Tier 1 활성화 시 최대 100~200Gbps 대역폭을 지원합니다.
  • Hyperdisk 동적 프로비저닝: 디스크 용량에 따라 IOPS가 고정되던 기존 Persistent Disk와 달리, Hyperdisk는 용량과 성능(IOPS, Throughput)을 분리하여 운영 중에도 무중단으로 성능을 조정할 수 있습니다.
  • Golden Image vs Startup Script: 오토스케일링 환경에서 부팅 시 패키지 설치를 수행하면 지연과 외부 의존성 장애가 발생합니다. Packer와 Cloud Build로 불변 이미지를 굽고, Startup Script는 환경변수 주입과 데몬 기동에만 사용합니다.

2. Global VPC와 엔터프라이즈 방화벽 및 접근 통제

AWS의 VPC는 리전 단위이고 서브넷이 가용 영역(AZ)에 귀속되지만, GCP의 VPC는 글로벌 리소스이며 서브넷이 리전 리소스입니다. 단일 리전 서브넷 하나로 해당 리전 내 모든 존(a, b, c)의 VM이 별도 라우팅 설정 없이 통신합니다.

구분 Network Tags Service Account 기반 방화벽 IAM Tags + Network Firewall Policy
식별 메커니즘 VM의 단순 텍스트 라벨 속성 VM에 부여된 IAM Service Account Resource Manager 차원의 키-값 태그 바인딩
보안 통제 수준 낮음 (`setTags` 권한 보유 시 임의 변경 가능) 높음 (`iam.serviceAccounts.actAs` 권한 필요) 매우 높음 (태그 바인딩 IAM 권한을 중앙 보안팀이 독점 통제)
운영 제약사항 실시간 변경 가능 SA 변경 시 VM 중지 필요, VPC Peering 미지원 무중단 실시간 변경 가능, 조직/폴더 계층 정책 및 Peering 지원
무키(Keyless) 보안 접근 표준: 프로덕션 VM에는 공인 IP를 할당하지 않고 Bastion Host도 두지 않습니다. `35.235.240.0/20` 대역에서 TCP 22번 인바운드만 허용한 뒤, OS Login(`enable-oslogin=TRUE`) + IAP Tunneling을 통해 IAM 권한과 리눅스 계정을 실시간 연동하여 접속합니다.

Session 2 Instance Group 구조 및 라이프사이클 운영

1. Regional MIG 멀티존 분산 알고리즘과 무중단 배포

Target Distribution Shape
  • EVEN: 리전 내 선택된 모든 존에 인스턴스 대수를 엄격히 균등 유지합니다.
  • BALANCED: 균등 배치를 우선하되 특정 존 용량 부족 시 가용한 타 존에 우선 생성하여 전체 목표 대수를 맞춥니다.
  • ANY: 존 균등성보다 가용 용량 확보나 예약 리소스 소비를 최우선으로 합니다.
Rolling & Canary Update
  • PROACTIVE: 템플릿 변경 즉시 롤링 교체를 실행합니다.
  • OPPORTUNISTIC: 스케일아웃이나 장애 복구 시에만 새 템플릿을 점진 반영합니다.
  • 단일 MIG 카나리: 별도 MIG 생성 없이 `versions` 블록에 v1과 v2(예: 10% 또는 고정 1대)를 동시 선언해 실트래픽을 검증합니다.
무중단 교체 필수 파라미터
  • maxUnavailable = 0: 새 VM이 완전히 준비되기 전까지 기존 VM 삭제를 금지합니다.
  • maxSurge >= 3: Regional MIG(3개 존)에서 존별 동시 생성을 보장합니다.
  • minReadySec: 헬스체크 통과 후 애플리케이션 워밍업 대기 시간을 확보합니다.
  • SUBSTITUTE: 새 VM을 먼저 띄운 뒤 기존 VM을 제거합니다.

2. Autohealing Health Check와 Load Balancer Health Check의 분리 설계

주의 (Cascading Failure 방지): Load Balancer 헬스체크와 MIG Autohealing 헬스체크에 동일한 엔드포인트를 사용하면 안 됩니다. 백엔드 DB 일시 지연 시 LB가 트래픽만 잠시 빼야 할 상황에서, Autohealer가 전체 WAS 인스턴스를 불량으로 판정해 동시에 강제 삭제 및 재부팅시키는 연쇄 장애가 발생합니다.
비교 항목 Load Balancer Health Check (Readiness) Autohealing Health Check (Liveness)
목적 현재 인스턴스가 클라이언트 트래픽을 정상 처리할 수 있는지 확인 데몬 크래시나 OS 행(Hang)으로 인해 VM 자체를 재설치해야 하는지 확인
실패 시 액션 LB 라우팅 풀에서 즉시 제외 (VM은 유지되며 정상화 시 즉시 재투입) VM 강제 삭제 후 새 VM 프로비저닝 (최소 수 분 소요)
권장 설정값 /healthz/ready · 5초 주기, 2회 연속 실패 시 Unhealthy (10초) /healthz/live · 10~15초 주기, 3~5회 연속 실패 시 트리거 + initialDelaySec 충분히 확보

3. Stateful MIG 아키텍처와 설계상 한계점

고정 내부/외부 IP, 영구 디스크(`autoDelete=false`), 인스턴스 이름과 고유 메타데이터를 보존해야 하는 레거시 솔루션이나 상태 유지형 노드에 사용합니다. 단, 프로덕션 도입 전 다음 3가지 제약사항을 반드시 검토해야 합니다:

  • Autoscaling 동시 사용 불가: 각 인스턴스가 고유 식별자와 디스크 상태를 보유하므로 자동 수평 확장을 활성화할 수 없습니다.
  • 교차 존 자동 페일오버 미지원: Stateful MIG의 Autohealing은 동일한 존 내부에서만 VM을 재생성하고 기존 Zonal 디스크를 재부착합니다. 존 전체 장애에 대비하려면 애플리케이션 레벨 복제를 구성해야 합니다.
  • 업데이트 시 `RECREATE` 강제: 동일한 이름과 IP, 디스크를 재사용해야 하므로 새 VM을 옆에 먼저 만드는 `SUBSTITUTE` 방식을 쓸 수 없고 기존 VM을 내렸다 올리는 `RECREATE`만 가능합니다.

Session 3 Cloud Load Balancing 아키텍처 및 트래픽 제어

1. GFE, Andromeda SDN, Maglev 및 Envoy 아키텍처

타 클라우드의 로드 밸런서가 고객 VPC 서브넷 내부에 가상 어플라이언스(노드)를 프로비저닝하는 방식인 것과 달리, Google Cloud Load Balancing은 전 세계 80개 이상의 PoP에 상시 가동 중인 GFE(Google Front End), Maglev 및 호스트 하이퍼바이저에 내장된 Andromeda SDN에 라우팅 구성을 배포하는 아키텍처입니다. 따라서 트래픽 급증 시 별도의 사전 워밍(Pre-warming) 없이 즉각적인 트래픽 수용이 가능합니다.

L4 엔진: Maglev vs Andromeda 직접 라우팅
  • External Passthrough NLB: Google의 분산 소프트웨어 L4 로드 밸런서인 Maglev가 일관된 해싱(Consistent Hashing)과 연결 추적을 통해 패킷을 백엔드 호스트로 분배합니다.
  • Internal Passthrough NLB: 별도의 프록시나 중간 LB 장비 홉을 거치지 않습니다. Andromeda SDN 컨트롤 플레인이 가상 스위치(`vswitch`)에 직접 경로를 프로그래밍하여 소스 VM 호스트에서 타겟 백엔드 VM 호스트로 패킷이 직접 전달됩니다.
L7 엔진: Classic GFE vs 차세대 Envoy 프록시
  • Classic ALB (EXTERNAL): 기존 GFE 독자 스택에서 동작합니다.
  • Global / Regional / Internal ALB (EXTERNAL_MANAGED, INTERNAL_MANAGED): 오픈소스 Envoy 프록시 데이터 플레인 위에서 동작하며 가중치 기반 카나리 스플리팅, 정규표현식 라우팅, 양방향 mTLS, Service Extensions를 지원합니다.
  • Proxy-only Subnet: 리전/내부 Envoy 프록시들이 고객 VPC의 백엔드 VM으로 연결을 맺을 때 출발지(SNAT) 주소로 사용하는 전용 서브넷 대역입니다.

2. Proxy LB vs Passthrough LB 패킷 흐름 및 DSR(Direct Server Return)

비교 항목 Proxy Load Balancer (L7 ALB, L4 Proxy NLB) Passthrough Load Balancer (External/Internal Passthrough NLB)
TCP/TLS 세션 종료 LB(GFE/Envoy)에서 클라이언트 연결을 종료하고 백엔드와 새 TCP 세션을 수립 LB는 세션을 종료하지 않고 원본 패킷을 백엔드 VM으로 그대로 전달
백엔드가 보는 Source IP LB 프록시 대역 (`35.191.0.0/16`, `130.211.0.0/22` 또는 Proxy-only Subnet) 클라이언트의 실제 원본 Source IP 보존
백엔드가 보는 Destination IP 백엔드 VM 자신의 Private NIC IP Load Balancer(Forwarding Rule)의 VIP
응답 패킷 경로 백엔드 VM → LB 프록시 → 클라이언트 Direct Server Return (DSR): 백엔드 VM이 클라이언트에게 직접 응답 전송
네트워크 엔지니어링 팁 (Passthrough LB에서 백엔드 VM이 LB VIP 패킷을 수신하는 원리):
패스스루 LB는 패킷의 목적지 IP를 백엔드 VM의 IP로 바꾸지(DNAT) 않고 LB VIP 그대로 전달합니다. 이때 백엔드 VM 내부의 google-guest-agent 데몬이 리눅스 커널의 local 라우팅 테이블(ip route show table local proto 66)에 LB VIP를 자동 등록하기 때문에 커널이 패킷을 드롭하지 않고 로컬 소켓으로 수신하며, 응답 시에도 출발지 IP를 LB VIP로 달아 DSR을 수행합니다.

3. 하이브리드 네트워크 연동 및 Cloud NAT 포트 고갈 방지

온프레미스/타 클라우드 연동 및 NVA 아키텍처
  • Internal LB Global Access: Dedicated Interconnect나 HA VPN 너머의 온프레미스 서버에서 GCP 내부의 Internal ALB/NLB VIP를 호출하려면 Forwarding Rule에 --allow-global-access 활성화가 필수입니다.
  • Internal NLB Next-hop 방화벽: 서드파티 보안 장비(NVA) MIG 앞에 Internal Passthrough NLB를 배치하고 VPC 라우팅 테이블의 Next-hop(--next-hop-ilb)으로 지정하면 BGP 수렴 지연 없는 고가용성 인라인 보안 계층을 구성할 수 있습니다.
Cloud NAT 동적 포트 할당 튜닝
  • Private VM이 외부 특정 목적지 IP:Port(예: 외부 결제/오픈뱅킹 API)로 대량의 동시 연결을 맺을 때 기본 정적 포트(64개) 설정은 즉시 포트 고갈(OUT_OF_RESOURCES)을 유발합니다.
  • 반드시 Dynamic Port Allocation을 활성화(minPortsPerVm=256~1024, maxPortsPerVm=65536)하고, enable_endpoint_independent_mapping = false 상태를 유지하며, 필요시 복수의 공인 NAT IP를 할당해야 합니다.

4. Balancing Mode 설계와 Keep-alive 502 Bad Gateway 방지 공식

L7 Application Load Balancer와 MIG를 연동할 때는 CPU 사용률만 보고 판단하는 UTILIZATION보다 인스턴스당 초당 요청 수를 제한하는 RATE 모드가 예측 가능성이 높습니다. 또한 가장 빈번한 프로덕션 장애 중 하나인 간헐적 502 에러를 막기 위해 아래 타임아웃 규칙을 반드시 준수해야 합니다.

  고정 Keep-Alive Idle Timeout = 600초                    기본 Keep-Alive Timeout = 5~65초 (미스매치!)
              |                                                          |
              | ---- (백엔드가 유휴 연결 종료를 위해 TCP FIN 전송) <---- |
              | ----> (동시 타이밍에 LB가 재사용 소켓으로 HTTP POST 전송) |
              | <---- (백엔드가 이미 닫힌 소켓이므로 TCP RST 응답) ------ |

   502 Bad Gateway 발생!

1. Load Balancer 로그 기반 구간별 병목 특정 및 statusDetails 해부

지연 시간이나 5xx 에러 발생 시 네트워크 구간 문제인지 백엔드 애플리케이션 문제인지 즉시 구분하는 핵심 필드입니다:

  • httpRequest.latency (total_latencies): 클라이언트 요청 첫 바이트가 LB에 도달한 시점부터 응답 마지막 바이트를 클라이언트에 전송 완료할 때까지의 전체 시간입니다.
  • jsonPayload.backend_target_latency (backend_latencies): LB 프록시가 백엔드 VM에 요청을 전달하고 응답을 수신하기까지 걸린 순수 백엔드 처리 시간입니다.
jsonPayload.statusDetails 값 HTTP 상태 정확한 원인 및 해결 방안
response_sent_by_backend 2xx ~ 5xx LB 구간 이상 없음. 백엔드 애플리케이션이 직접 반환한 응답 코드입니다.
backend_connection_closed_before_data_sent_to_client 502 Keep-alive 타임아웃 미스매치. 백엔드가 유휴 TCP 연결을 먼저 끊음 → 백엔드 Keep-alive를 620초로 설정합니다.
failed_to_connect_to_backend 502 LB가 백엔드 VM과 TCP 연결 수립 실패. 방화벽(`35.191.0.0/16`, `130.211.0.0/22`, Proxy-only Subnet) 차단 또는 백엔드 프로세스 다운을 확인합니다.
backend_timeout 504 백엔드 연결은 성공했으나 Backend Service의 timeoutSec(기본 30초) 내에 응답하지 못함 → 백엔드 슬로우 쿼리 점검 또는 타임아웃 상향.
failed_to_pick_backend 502 / 503 가용한 Healthy 백엔드가 0대임 → Health Check 경로/포트 및 방화벽 규칙을 즉시 점검합니다.

Cloud Shell 또는 로컬 터미널에서 실습 레포지토리를 클론하고, VPC, 동적 포트 할당이 적용된 Cloud NAT, Private Regional MIG, Envoy 기반 Global External ALB를 한 번에 생성합니다.

Step 2. Private VM IAP 터널링 접속 및 Connectivity Tests 검증 gcloud CLI

생성된 MIG 인스턴스는 공인 IP가 전혀 없습니다. IAP TCP Forwarding을 통해 SSH 접속이 이루어지는지 확인하고, Network Intelligence Center의 Connectivity Tests로 Google Health Check 대역에서 백엔드 VM 8080 포트로의 방화벽 및 라우팅 정합성을 검증합니다.

# 1. MIG 내 첫 번째 인스턴스 이름 및 존 확인
VM_INFO=$(gcloud compute instance-groups managed list-instances gce-ws-rmig \
  --region=$REGION --format="value(instance.basename(),instance.scope().segment(0))" | head -n 1)
VM_NAME=$(echo $VM_INFO | awk '{print $1}')
VM_ZONE=$(echo $VM_INFO | awk '{print $2}')

# 2. 공인 IP 없이 IAP Tunneling으로 내부 상태 및 Keep-Alive 설정 확인
gcloud compute ssh "$VM_NAME" --zone="$VM_ZONE" --tunnel-through-iap \
  --command="systemctl status workshop-app --no-pager && curl -s localhost:8080 | jq ."

# 3. Connectivity Test 생성 및 실행 (Health Check Prober -> Private VM:8080)
gcloud network-management connectivity-tests create hc-to-vm-test \
  --source-ip-address=35.191.0.1 \
  --destination-instance="projects/${PROJECT_ID}/zones/${VM_ZONE}/instances/${VM_NAME}" \
  --destination-port=8080 \
  --protocol=TCP

gcloud network-management connectivity-tests describe hc-to-vm-test \
  --format="yaml(reachabilityDetails)"

Step 4. Keep-Alive 타임아웃 미스매치(502 Bad Gateway) 장애 주입 및 디버깅 Troubleshooting

백엔드 Keep-Alive 타임아웃을 의도적으로 2초로 낮추어 LB(600초)와의 Race Condition을 유발하고, Cloud Logging에서 backend_connection_closed_before_data_sent_to_client 시그니처를 확인한 뒤 620초로 복구합니다.

# 1. 백엔드 Keep-Alive 타임아웃을 2초로 단축하여 취약한 템플릿 배포
terraform apply -var="project_id=${PROJECT_ID}" -var="app_version=v2-buggy" -var="keepalive_timeout_sec=2" -auto-approve

# 2. 롤링 업데이트 완료 대기
gcloud compute instance-groups managed wait-until --stable gce-ws-rmig --region=$REGION

# 3. 2초 유휴 경계 타이밍에 POST 요청을 보내 502 Bad Gateway 재현
python3 ../scripts/trigger_502_race.py "$ALB_VIP" 1.98

# 4. Cloud Logging에서 502 에러의 정확한 원인(statusDetails) 및 지연 시간 쿼리
gcloud logging read \
  'resource.type="http_load_balancer" AND httpRequest.status>=500' \
  --limit=5 \
  --format="table(timestamp, httpRequest.status, jsonPayload.statusDetails, httpRequest.latency, jsonPayload.backend_target_latency)"

# 5. 황금 공식(Keep-Alive 620초 > LB 600초)으로 복구 후 502 소멸 검증
terraform apply -var="project_id=${PROJECT_ID}" -var="app_version=v2-fixed" -var="keepalive_timeout_sec=620" -auto-approve
