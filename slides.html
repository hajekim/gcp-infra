1.1 세대별 머신 시리즈(C3/C4, N2/N4, E2)와 Titanium 오프로딩

맥락(Why): 가상머신 도입 시 가장 먼저 우려하는 것은 "호스트 하이퍼바이저가 내 CPU를 뺏어 쓰며 발생하는 응답 지연 편차(Tail Latency Jitter)"입니다. 3/4세대 머신(C3, C4, N4)은 이를 어떻게 하드웨어 수준에서 제거했을까요?
기존 호스트 CPU 가상화 vs 3/4세대 Titanium IPU 하드웨어 오프로딩 비교 
[기존 세대 (N1/N2)]   게스트 VM vCPU  +  호스트 하이퍼바이저 에뮬레이션(네트워크/스토리지 I/O) ──▶ 동일 물리 CPU 공유 (I/O 집중 시 지터 발생)
[3/4세대 (C3/C4/N4)] 게스트 VM vCPU (100% 고객 워크로드 전용)  │  별도 Titanium IPU 전용 칩 (Andromeda SDN + Hyperdisk NVMe + 암호화 전담)
머신 시리즈 프로세서 및 아키텍처 핵심 동작 특성 권장 워크로드 및 선택 기준
C3 / C4 / C3D
(Compute-Optimized)		 Intel Sapphire/Emerald Rapids, Granite Rapids, AMD EPYC Genoa + Titanium IPU 네트워크·스토리지 가상화를 Titanium 전용 칩으로 완전 분리. 일관된 고클럭과 가장 낮은 응답 시간 편차 보장 고성능 API 게이트웨이, 대규모 트랜잭션 WAS, 인메모리 캐시(Redis), 실시간 데이터 처리
N2 / N2D / N4
(General-Purpose)		 Intel Cascade/Ice Lake, Emerald Rapids(N4), AMD Milan 균형 잡힌 vCPU 대 메모리 비율(1:4 기본, 최대 1:8 확장). N4는 Titanium 및 Hyperdisk 기본 탑재 표준 엔터프라이즈 웹/애플리케이션 서버, 중규모 데이터베이스, 마이크로서비스 백엔드
E2
(Cost-Optimized)		 호스트 가용 자원에 따른 동적 플랫폼 할당 N2 대비 약 31% 저렴한 비용. Sustained Use Discount 대신 처음부터 낮은 기본 단가 제공 개발/스테이징(Dev/QA) 환경, 백오피스, 트래픽 편차가 완만한 무상태 경량 서비스
핵심 요약지연 시간에 민감한 프로덕션 핵심 티어는 Titanium IPU가 I/O를 오프로딩하는 C3/C4 또는 N4 시리즈를 표준으로 채택합니다.

1.2 VirtIO의 한계를 넘는 gVNIC과 대역폭 산정 공식

맥락(Why): Titanium IPU로 호스트의 네트워크 처리를 가속했더라도, 정작 게스트 OS 안의 가상 랜카드 드라이버가 구형 VirtIO라면 32~50Gbps 이상에서 CPU 인터럽트 병목이 발생합니다.
왜 gVNIC이 엔터프라이즈 필수 표준인가?
  • Andromeda SDN 직접 연동: 레거시 VirtIO 에뮬레이션 계층을 거치지 않고 호스트의 Andromeda 가상 스위치 및 Titanium IPU와 직접 메모리 버퍼(DMA)를 교환합니다.
  • 3세대 이상 머신 필수 요건: C3, C4, N4, C3D 등 최신 머신 시리즈는 커스텀 이미지 생성 시 반드시 --guest-os-features=GVNIC 태그가 포함되어야 부팅됩니다.
  • 멀티 큐(RSS) 스케일링: 패킷 인터럽트를 단일 코어에 몰아넣지 않고 전체 vCPU 코어로 고르게 분산하여 패킷 드롭(softirq 병목)을 방지합니다.
VM 이그레스(Egress) 대역폭 산정 공식
  • 기본 대역폭 공식: vCPU 1개당 2 Gbps씩 선형 증가
  • 표준 상한선 (기본값): 머신 시리즈에 따라 최대 32 Gbps ~ 100 Gbps에서 캡(Cap) 적용
  • Tier 1 고대역폭 활성화 시: 대형 C3/C4/C3D 인스턴스에서 --network-performance-configs=total-egress-bandwidth-tier=TIER_1 옵션을 켜면 최대 100 Gbps ~ 200 Gbps까지 대역폭 상한이 확장됩니다.
  • 인바운드(Ingress): GCP VPC 내부에서 VM으로 들어오는 인바운드 대역폭은 별도 과금이나 소프트웨어 스로틀링 없이 수신측 처리 한계까지 열려 있습니다.
게스트 OS 내부에서 gVNIC 드라이버 및 멀티 큐 작동 상태 확인 
$ ethtool -i ens4
driver: gve          # Google Virtual Ethernet (gVNIC) 커널 드라이버 활성화 확인
version: 1.0.0
핵심 요약사내 표준 Golden Image 파이프라인(Packer)에는 반드시 GVNIC 피처 플래그를 기본 내장해야 최신 머신 패밀리와 Tier 1 대역폭을 사용할 수 있습니다.

1.3 하드웨어 점검 시 VM을 살리는 Live Migration 메커니즘

맥락(Why): 물리 서버의 펌웨어 패치나 하드웨어 결함 예고 시, 타 클라우드에서는 종종 인스턴스 재부팅 안내 메일을 받고 새벽 작업을 해야 합니다. GCE는 어떻게 재부팅과 IP 변경 없이 실행 중인 VM을 옆 물리 서버로 옮길까요?
GCE 무중단 Live Migration 3단계 메모리 동기화 타임라인 
[1. Pre-Copy 단계] VM이 정상 서비스 중인 상태에서 백그라운드로 메모리 페이지들을 신규 물리 호스트로 사전 복사
        │
[2. Blackout 단계] 변경된 마지막 메모리 조각(Dirty Pages)과 CPU 레지스터 상태만 순간 전환 (수십~수백 ms 이내, TCP 세션 유지)
        │
[3. Post-Copy 완료] Andromeda SDN이 해당 VM의 가상 NIC 라우팅 포인터를 신규 물리 호스트로 즉시 갱신 (재부팅 없음, IP/MAC 그대로 유지)
Live Migration 지원 대상 (기본값)
  • 일반 범용·컴퓨팅·메모리 최적화 VM (C3, C4, N2, N4, E2, M3 등)
  • 유지보수 정책: onHostMaintenance = MIGRATE, automaticRestart = TRUE
  • 물리 호스트 장애 징후나 정기 하이퍼바이저 패치 시 운영자 개입이나 재부팅 없이 투명하게 다른 물리 서버로 이동합니다.
Live Migration 불가 (Terminate 대상 워크로드)
  • 물리 하드웨어가 호스트에 직결된 경우: GPU 장착 VM(A2/A3/G2), 대용량 Local SSD 연결 VM 일부, 베어메탈(-metal), Confidential VM 일부
  • 호스트 점검 시 VM이 중지(TERMINATE)된 후 타 호스트에서 재시작됩니다.
  • 필수 대응책: 메타데이터 서버(instance/maintenance-event)를 폴링하여 종료 60분 전 알림을 감지하고 Connection Draining을 선제 수행해야 합니다.
핵심 요약표준 WAS/API 서버는 Live Migration으로 무중단 보호되며, GPU·대용량 Local SSD 노드만 메타데이터 이벤트 감지 데몬을 붙여 우아한 퇴거를 구현합니다.

1.4 네트워크 블록 스토리지의 진화: Persistent Disk vs Hyperdisk

맥락(Why): 기존 Persistent Disk(PD)에서는 높은 IOPS를 얻으려면 필요하지도 않은 수 테라바이트의 디스크 용량을 억지로 늘려야 했습니다. 차세대 Hyperdisk는 어떻게 용량과 성능을 완전히 분리했을까요?

1.5 오토스케일링 생존율을 결정하는 Golden Image 파이프라인

1.6 리전과 존의 경계를 허무는 Global VPC와 Shared VPC 구조

맥락(Why): 타 클라우드에서는 가용 영역(AZ)마다 서브넷 CIDR을 쪼개고, 계정마다 VPC를 만든 뒤 Transit Gateway로 묶느라 라우팅 테이블과 게이트웨이 비용이 기하급수적으로 늘어납니다. GCP는 왜 다를까요?
타 클라우드(AZ별 서브넷 분리) vs Google Cloud(리전 단위 단일 서브넷 + Global VPC) 
[타 클라우드 VPC]  리전 종속 VPC ──▶ AZ-a 서브넷(10.0.1.0/24) / AZ-b 서브넷(10.0.2.0/24) / AZ-c 서브넷(10.0.3.0/24) (존 이동 시 IP 대역 변경 강제)
[Google Cloud VPC] 글로벌 단일 VPC ──▶ 서울 리전 단일 서브넷(10.10.0.0/20)이 Zone A, Zone B, Zone C 전체를 포괄 (동일 대역에서 멀티존 HA 구성)
Global VPC + 리전 단일 서브넷의 이점
  • 단일 CIDR로 3개 존(Zone) 커버: 서브넷이 존(Zone)이 아닌 리전(Region) 리소스이므로, 존별 IP 고갈 걱정 없이 하나의 서브넷 위에서 멀티존 클러스터(Regional MIG)를 운영합니다.
  • 글로벌 동적 라우팅 (GLOBAL 모드): 서울 리전에만 전용선(Interconnect)과 Cloud Router를 연결해도, 동일 VPC 내 도쿄/미국 리전의 서브넷까지 별도 피어링 없이 BGP로 자동 광고·통신됩니다.
엔터프라이즈 표준: Shared VPC 권한 분리
  • Host Project (네트워크/보안팀 전담): 중앙 VPC, 서브넷, 전용선/VPN, Cloud NAT, 계층형 방화벽을 중앙에서 독점 관리합니다.
  • Service Project (서비스 개발팀): 각 서비스팀은 독립된 프로젝트에서 VM과 MIG를 생성하되, 네트워크 인터페이스만 Host Project의 특정 서브넷에 연결(roles/compute.networkUser)합니다.
  • 비용 및 성능 이점: 동일 리전 내 Shared VPC 간 통신은 별도의 Transit Gateway 어태치먼트 비용이나 홉 지연 없이 Andromeda SDN 위에서 직접 통신합니다.
핵심 요약서브넷이 3개 존에 걸쳐 있다는 특성은 다음 세션에서 다룰 Regional MIG와 Stateful 고정 IP 보존을 가능케 하는 핵심 기반입니다.

2.1 UMIG vs Regional MIG와 멀티존 분산 알고리즘(Shape)

맥락(Why): Session 1에서 만든 단일 서브넷은 리전 내 3개 존(Zone A/B/C)에 걸쳐 있습니다. 이 위에서 단일 존 장애(Zone Outage)가 발생해도 서비스가 중단되지 않으려면 인스턴스들을 어떤 구조로 묶고 분산해야 할까요?
구분 Unmanaged IG (UMIG) Zonal MIG (단일 존 관리형) Regional MIG (멀티존 관리형 · 권장)
핵심 특징 및 용도 서로 다른 스펙의 수동 VM 묶음. 오토스케일링·자동 복구·롤링 업데이트 불가 (레거시 수동 서버 LB 연결용) 단일 존 내부에서만 템플릿 기반 생성·복구. 해당 존 장애 시 그룹 전체 중단 (고성능 HPC 등 초저지연 클러스터용) 1개 서브넷 위에서 3개 존(Zone A/B/C)에 인스턴스를 자동 분산. 특정 존 장애 시 나머지 정상 존으로 용량 유지
1. EVEN (기본값 · 무상태 표준)
  • 3개 존에 인스턴스 대수를 정확히 1/3씩 균등하게 맞춥니다.
  • Proactive Redistribution을 켜면 존 간 불균형 발생 시 자동으로 VM을 재배치하여 33:33:33 비율을 강제합니다.
2. BALANCED (재고 부족 방어)
  • 기본적으로 균등 분산을 추구하되, 특정 존에 일시적 하드웨어 재고 부족(Stockout) 발생 시 가용 자원이 있는 다른 존에 먼저 VM을 생성해 전체 목표 대수를 사수합니다.
3. ANY / ANY_SINGLE_ZONE
  • ANY: 존 균형과 무관하게 가장 빨리 띄울 수 있는 곳에 생성 (배치 작업용)
  • ANY_SINGLE_ZONE: 가용한 하나의 존을 골라 모든 노드를 몰아넣어 교차 존 네트워크 지연을 제거합니다.
핵심 요약프로덕션 WAS/API 티어는 Regional MIG (EVEN 또는 BALANCED)를 표준으로 채택하며, 로컬 캐시 의존도가 높다면 Proactive Redistribution을 비활성화합니다.

2.2 불변 템플릿과 Rolling Update 무중단 배포 공식

맥락(Why): GCE의 Instance Template은 한 번 만들면 수정할 수 없는 불변(Immutable) 리소스입니다. 새 버전의 템플릿(`v2`)을 배포할 때 단 1건의 요청 실패도 없이 넘어가는 파라미터 조합 공식은 무엇일까요?
Surge Rolling Update 무중단 교체 타임라인 (maxUnavailable = 0, maxSurge = 3) 
[단계 1: Surge 생성] 기존 v1 인스턴스 6대는 100% 유지한 채, 3개 존에 신규 v2 인스턴스 3대를 추가 생성 (총 9대 가동)
        │
[단계 2: Readiness & Warm-up] 신규 v2 인스턴스가 LB Health Check를 통과한 직후 minReadySec(예: 60초) 동안 JIT 컴파일 및 커넥션 풀 예열
        │
[단계 3: 구버전 Draining] 신규 v2가 트래픽을 정상 처리하면 비로소 구버전 v1 인스턴스 3대에 Connection Draining 후 종료
반드시 지켜야 할 3대 파라미터 공식
  • 1. maxUnavailable = 0: 배포 중에도 기존 처리 용량이 100% 아래로 떨어지지 않도록 강제합니다.
  • 2. Regional MIG에서 maxSurge >= 3: 3개 존(Zone A/B/C)에서 동시에 1대씩 병렬로 새 버전을 띄우려면 최소 존 개수(3) 이상으로 설정해야 배포 시간이 1/3로 단축됩니다.
  • 3. minReadySec 설정: 프로세스 포트만 열렸다고 바로 구버전을 죽이지 않도록, JVM/앱 예열 시간(30~60초)을 부여합니다.
교체 방식: SUBSTITUTE vs RECREATE
  • SUBSTITUTE (기본값 · 무상태 권장): 새로운 이름과 IP를 가진 새 VM을 옆에 먼저 띄운 뒤 기존 VM을 삭제합니다. 가장 빠르고 안전합니다.
  • RECREATE (Stateful 필수): 기존 VM의 이름·고정 IP·디스크를 그대로 물려받아야 할 때 사용합니다. 기존 VM을 먼저 내려야 하므로 maxUnavailable=0과 함께 쓸 수 없습니다.
핵심 요약무상태 서비스의 롤링 업데이트 표준 공식은 type=PROACTIVE + maxUnavailable=0 + maxSurge=3(또는 20%) + replacementMethod=SUBSTITUTE입니다.

발표자 노트 실무에서 Regional MIG에 `maxSurge=1`을 넣어서 배포가 한 존씩 순차 진행되느라 3배로 느려지는 경우가 많습니다. 3개 존 Regional MIG에서는 `maxSurge`를 최소 3(존당 1대) 이상으로 주어야 병렬 롤아웃이 된다는 팁을 강조하세요.

2.3 리스크를 통제하는 2가지 카나리(Canary) 배포 패턴

맥락(Why): 전체 인스턴스를 한 번에 롤링 업데이트하기 부담스러운 대규모 변경에서는 일부 인스턴스(예: 10%)에만 먼저 신규 버전을 올려 에러율을 검증해야 합니다. GCP에서는 어떤 두 가지 방식이 있을까요?
패턴 A: 단일 MIG 내 다중 템플릿 버전 분할 (Built-in Canary)
  • 하나의 MIG 안에서 기본 버전(v1) 외에 카나리 버전(v2)의 targetSize를 고정 대수 또는 비율(예: 10%)로 지정합니다.
  • 장점: 별도의 인프라 리소스 추가 없이 명령어 한 줄로 즉시 카나리 배포 및 롤백이 가능합니다.
  • 한계: 카나리 비율이 인스턴스 대수 기준으로만 결정되므로, HTTP 헤더(`X-Canary: true`) 기반 라우팅이나 1% 미만의 미세 트래픽 제어는 불가합니다.
단일 MIG 내 10% 카나리 배포 명령 
gcloud compute instance-groups managed rolling-action start-update was-mig   --version=template=was-tpl-v1   --canary-version=template=was-tpl-v2,target-size=10%
패턴 B: 별도 카나리 MIG 분리 + ALB 가중치 라우팅
  • 안정 버전용 prod-mig-stable과 카나리 전용 prod-mig-canary를 별도 그룹과 별도 Backend Service로 분리합니다.
  • Application Load Balancer(Envoy 기반)의 URL Map에서 weightedBackendServices(가중치 99:1) 또는 특정 쿠키/헤더 매칭 규칙으로 트래픽을 분기합니다.
  • 장점: 인스턴스 대수와 무관하게 0.5%, 1% 단위의 정밀한 트래픽 가중치 조절 및 사내 테스트 헤더 분기가 가능합니다.
ALB URL Map 기반 가중치 분기 구조 
[ALB URL Map] ─┬─▶ 99% 가중치 ──▶ Backend Service A (stable MIG)
               └─▶  1% 가중치 ──▶ Backend Service B (canary MIG)
핵심 요약일반적인 정기 배포는 패턴 A(단일 MIG 내 카나리)로 단순하게 운영하고, 결제/코어 API처럼 헤더 기반 검증과 1% 단위 제어가 필요한 경우 패턴 B를 선택합니다.

2.4 예측형 스케일링과 급격한 축소를 막는 Scale-in Control

맥락(Why): 트래픽이 빠졌다고 오토스케일러가 100대이던 서버를 단 2분 만에 20대로 확 줄여버리면, 살아남은 20대의 로컬 캐시가 깨지고 2차 트래픽 유입 시 커넥션 스톰으로 장애가 납니다.
다중 지표 결합 및 예측형 스케일링
  • 다중 시그널 OR 평가: CPU 사용률(예: 60%), LB 용량 사용률, Cloud Monitoring 커스텀 메트릭(예: 메시지 큐 적체 건수)을 동시에 등록하면, 가장 큰 대수를 요구하는 지표를 따라 안전하게 확장합니다.
  • 초기화 시간(coolDownPeriodSec): Golden Image 부팅부터 앱이 정상 트래픽을 받을 때까지 걸리는 시간(예: 60~90초)으로 설정해 부팅 중 CPU 100%에 의한 과잉 확장을 막습니다.
  • 예측형 스케일링 (OPTIMIZE_AVAILABILITY): 일간/주간 트래픽 패턴을 학습해 피크 타임 도달 전에 미리 VM을 띄워둡니다.
프로덕션 필수 안전장치: Scale-in Control
  • Scale-out은 즉각적으로, Scale-in은 보수적으로!
  • timeWindowSec(예: 600초) 동안 관측된 최대 권장 인스턴스 수를 기준으로, 한 번에 줄어들 수 있는 최대 대수(maxScaledInReplicas)를 제한합니다.
  • 예: 최근 10분간 피크가 100대였고 축소 한도를 20%로 설정하면, 트래픽이 0으로 떨어져도 10분 동안 절대 80대 미만으로 내려가지 않고 완만하게 계단식으로 축소됩니다.
gcloud CLI · 최근 10분 피크 대비 최대 20%까지만 축소를 허용하는 Scale-in Control 적용 
gcloud compute instance-groups managed update-autoscaling prod-was-mig   --region=asia-northeast3   --scale-in-control=max-scaled-in-replicas-percent=20,time-window=600
핵심 요약프로덕션 MIG에는 반드시 scale_in_control을 설정하여 일시적 트래픽 골짜기(Dip)에서 서버가 대량 삭제되는 플래핑(Flapping)을 차단해야 합니다.

2.5 왜 Autohealing과 LB Health Check를 절대 합치면 안 되는가?

맥락(Why): 쿠버네티스에서 Liveness Probe와 Readiness Probe를 구분하듯, GCE에서도 MIG Autohealing 헬스 체크와 Load Balancer 헬스 체크의 목적과 실패 시 액션은 완전히 다릅니다.
안티 패턴: DB 연결 확인(/healthz/db)을 Autohealing 헬스 체크에 그대로 연결했을 때의 연쇄 재앙 
[백엔드 DB 30초 순단 발생] ──▶ 모든 WAS VM이 /healthz/db에 500 응답 반환
  ├─▶ [LB Health Check라면]  단순히 트래픽 라우팅만 일시 보류하거나 페일오버 동작 (DB 복구 즉시 1초 만에 전체 정상화!)
  └─▶ [Autohealing에 썼다면] MIG 컨트롤러가 "모든 WAS VM이 고장났다!"고 판단해 전체 WAS VM을 동시에 삭제 및 재생성 (전면 장애!)
비교 항목 Load Balancer Health Check (Readiness · 트래픽 수신 준비) MIG Autohealing Health Check (Liveness · VM 생존 여부)
핵심 질문 "지금 이 VM에 고객 요청을 보내도 정상 처리할 수 있는가?" "이 VM의 로컬 데몬이 완전히 죽어서 장비를 부수고 새로 만들어야 하는가?"
실패 시 동작 해당 VM으로 가는 신규 트래픽만 즉시 차단 (VM은 삭제하지 않고 계속 헬스 체크 폴링) 해당 VM을 강제 삭제(Delete)하고 새 VM을 처음부터 재생성(Recreate)
권장 엔드포인트 및 주기 /healthz/ready (워밍업 완료, 필수 의존성 상태, 우아한 종료 플래그 반영)
주기: 빠르고 민감하게 (interval=5s, unhealthyThreshold=2 -> 10초 내 격리)		 /healthz/live (외부 DB/API는 절대 보지 않고 오직 로컬 프로세스 생존만 확인)
주기: 보수적이고 여유 있게 (interval=15~30s, unhealthyThreshold=3~5)
골든 룰Autohealing 엔드포인트(/healthz/live)에는 외부 DB, Redis, 타 마이크로서비스 연결 체크 로직을 절대 넣지 마십시오.

2.6 배포·축소 시 패킷 유실 0건을 만드는 Graceful Shutdown 공식

맥락(Why): 롤링 업데이트나 스케일 인으로 VM이 내려갈 때, 아직 처리 중인 결제 요청이 끊기거나 LB가 이미 죽어가는 VM으로 새 요청을 보내는 현상을 어떻게 막을 수 있을까요?
LB Connection Draining과 VM Shutdown Script의 시간차 동기화 타임라인 
[T = 0초]   MIG가 VM 삭제 시작 ──▶ 1) LB가 즉시 해당 VM으로의 신규 연결 차단 (Connection Draining 타이머 예: 60초 시작)
                               ──▶ 2) 동시에 게스트 OS 내부에서 google-guest-agent가 Shutdown Script 실행
[T = 1~5초] Shutdown Script가 로컬 /healthz/ready 상태를 503으로 바꾸고 5초 대기 (인플라이트 패킷 유입 완전 차단 보장)
[T = 5~40초] 웹서버/WAS에 SIGTERM(nginx -s quit)을 보내 기존 연결의 트랜잭션이 끝날 때까지 우아하게 대기 후 프로세스 종료
[T = 60초]  LB Connection Draining 만료 및 VM 안전 삭제 완료 (클라이언트 에러 0건)
1단계: Backend Service Connection Draining
  • 로드 밸런서의 Backend Service에 --connection-draining-timeout=60s(최대 3600초 가능)를 설정합니다.
  • MIG에서 인스턴스 삭제가 트리거되는 순간 LB는 새 요청 유입을 막고, 기존에 맺어진 TCP 세션이 완료될 때까지 지정된 시간을 기다려 줍니다.
2단계: 게스트 OS Shutdown Script 연동
  • 단순히 OS가 바로 SIGKILL로 앱을 죽이지 않도록, Shutdown Script에서 먼저 /healthz/ready를 실패 상태로 만든 뒤 sleep 5 후 SIGTERM을 호출합니다.
  • 이를 통해 LB 제어 플레인의 전파 지연(1~3초) 동안 들어올 수 있는 마지막 요청까지 100% 안전하게 처리합니다.
핵심 요약무중단 배포의 완성은 새 서버를 띄우는 것(Surge)뿐만 아니라, 내려가는 서버의 Connection Draining + Shutdown Script를 맞추는 데 있습니다.

2.7 고정 IP와 디스크를 보존하는 Stateful MIG와 3대 구조적 한계

맥락(Why): 금융권 대외계 연동처럼 방화벽 화이트리스트 때문에 고정 IP가 필수이거나, 호스트명과 데이터 디스크가 그대로 유지되어야 하는 워크로드도 MIG의 자동 복구(Autohealing) 혜택을 받을 수 있을까요?
Stateful MIG가 보존하는 4가지 상태
  • 1. 인스턴스 이름 보존: VM이 재생성되어도 동일한 호스트명 유지
  • 2. 영구 디스크(PD/Hyperdisk) 보존: VM 장애로 삭제 후 재생성될 때 기존 디스크를 지우지 않고 새 VM에 그대로 재부착 (autoDelete=false)
  • 3. 내부 및 외부 고정 IP 보존: 장애 복구 후에도 동일한 사설/공인 IP 주소를 그대로 재할당
  • 4. Per-instance 메타데이터 보존: broker_id=1 등 노드별 고유 설정값 유지
도입 전 반드시 알아야 할 3대 구조적 제약사항
  • 1. Autoscaling 동시 사용 불가: 각 노드가 고유 상태와 디스크를 가지므로 자동 수평 확장(Autoscaling)을 켤 수 없습니다.
  • 2. 교차 존(Cross-Zone) 자동 페일오버 불가: Autohealing은 장애가 난 바로 그 존(Zone) 안에서만 VM을 다시 띄우고 디스크를 재부착합니다. 존 전체가 죽으면 타 존으로 자동 이동하지 않습니다.
  • 3. 업데이트 시 RECREATE 강제: 동일한 이름·IP·디스크를 새 VM에 물려야 하므로 기존 VM을 먼저 내렸다가 올리는 순단 방식만 가능합니다.
운영자 주의사항: 단일 VM API(compute instances)가 아닌 반드시 MIG API(instance-groups managed)로 제어할 것!

3.1 GFE, Andromeda SDN, Maglev, Envoy 기반 소프트웨어 정의 아키텍처

맥락(Why): 타 클라우드의 로드 밸런서는 고객 VPC 서브넷 안에 가상 어플라이언스(인스턴스)를 띄우므로 급격한 트래픽 유입 시 LB 자체가 스케일 아웃되는 데 수 분이 걸립니다. GCP는 왜 사전 예열(Pre-warming)이 필요 없을까요?
Google Cloud Load Balancing 글로벌 엣지 및 호스트 SDN 데이터 플레인 
[인터넷 클라이언트] ──(단일 Anycast VIP)──▶ [전 세계 80+ 엣지 PoP: Maglev (L4 해싱) + GFE / Envoy (L7 종료·WAF)]
                                                        │ (Google 글로벌 광케이블 백본 최단 경로 진입)
                                                        ▼
                                       [고객 VPC 호스트 하이퍼바이저: Andromeda SDN] ──▶ [백엔드 MIG VM / NEG]
1. Maglev (L4 분산 해싱)
  • 엣지 PoP 최전방의 소프트웨어 L4 패킷 분산기입니다.
  • Consistent Hashing으로 중앙 상태 동기화 없이 수백 대의 노드가 동일한 백엔드로 패킷을 보내며, 초당 수백만 RPS를 예열 없이 즉시 수용합니다.
2. GFE (Google Front End)
  • 사용자와 가장 가까운 엣지 PoP에서 TCP/TLS 핸드셰이크를 즉시 종료합니다.
  • 해외/원거리 클라이언트의 초기 연결 RTT 지연을 대폭 줄이고 L3/L4 DDoS 공격을 엣지에서 흡수합니다.
3. Envoy (L7 트래픽 엔진)
  • 차세대 External/Regional/Internal ALB(`*_MANAGED`)의 데이터 플레인입니다.
  • 정교한 헤더 조작, 정규식 라우팅, 가중치 카나리 분기, 서킷 브레이커, 상호 TLS(mTLS)를 제공합니다.
4. Andromeda SDN
  • Internal Passthrough NLB는 아예 중간 프록시 서버가 없습니다.
  • 클라이언트 VM이 속한 호스트의 가상 스위치(Andromeda)가 목적지 VIP를 보고 백엔드 VM 호스트로 워프하듯 직접 캡슐화 전송합니다.
핵심 요약Google Cloud LB는 고객 VPC 안에 갇힌 가상 장비가 아니라 전 세계 엣지와 SDN에 상시 가동 중인 거대한 공유 패브릭에 라우팅 규칙을 배포하는 방식입니다.

3.3 Proxy LB(연결 종료·재수립) vs Passthrough LB(DSR) 패킷 비교

맥락(Why): 백엔드 애플리케이션에서 getRemoteAddr()를 찍었을 때 어떤 LB는 프록시 IP가 찍히고, 어떤 LB는 실제 클라이언트의 원본 IP가 그대로 찍힙니다. 두 아키텍처의 패킷 헤더는 어떻게 다를까요?
패킷 헤더(Src IP / Dst IP) 및 TCP 세션 경계 비교 
[1. Proxy LB (ALB / Proxy NLB)]      클라이언트(203.0.113.5) ──(TCP 세션 #1: Dst=VIP)──▶ [GFE/Envoy 프록시] ──(별도 TCP 세션 #2: Src=프록시SNAT, Dst=VM_IP)──▶ [백엔드 VM]
[2. Passthrough LB (Passthrough NLB)] 클라이언트(203.0.113.5) ──(단일 TCP 세션 유지: Src=203.0.113.5, Dst=LB_VIP 그대로!)──(Andromeda SDN 캡슐화)──▶ [백엔드 VM]
비교 항목 Proxy 기반 LB (Application LB, Proxy Network LB) Passthrough 기반 LB (External / Internal Passthrough NLB)
TCP / TLS 세션 처리 프록시(GFE/Envoy)에서 클라이언트 연결을 완전히 종료(Terminate)하고, 백엔드 VM과 새로운 TCP 연결을 수립 연결을 종료하지 않고 클라이언트가 보낸 원본 패킷 그대로 Andromeda SDN을 통해 백엔드 VM에 직접 전달
백엔드가 보는 Src / Dst IP • Src IP: GFE 대역 또는 Proxy-only Subnet IP (SNAT됨)
• Dst IP: 백엔드 VM 자신의 Private NIC IP (10.10.1.5)		 • Src IP: 클라이언트 원본 IP 100% 보존!
• Dst IP: VM IP가 아닌 로드 밸런서의 VIP 주소 그대로 도착!
클라이언트 원IP 확인 방법 L7 ALB는 X-Forwarded-For 헤더, L4 Proxy NLB는 PROXY protocol v1/v2 헤더 파싱 필요 별도 헤더 파싱 없이 소켓 레이어(L3 헤더)에서 즉시 원본 IP 확인 가능
응답 패킷 경로 백엔드 VM → 프록시(Envoy/GFE) → 클라이언트 (대칭 경로) 백엔드 VM이 LB를 다시 거치지 않고 클라이언트에게 직접 응답(DSR, Direct Server Return)
핵심 질문Passthrough LB에서 목적지 IP가 내 VM IP(10.10.1.5)가 아닌 LB VIP(10.10.99.99)로 날아오는데, 왜 리눅스 커널이 이 패킷을 버리지(Drop) 않을까요?

3.4 왜 백엔드 VM은 목적지가 LB VIP인 패킷을 드롭하지 않는가?

맥락(Why): 온프레미스 L4 스위치에서 DSR(Direct Server Return)을 구성할 때는 모든 서버의 Loopback 인터페이스에 VIP를 수동 등록하고 ARP 응답을 꺼야 했습니다. GCE는 이를 어떻게 완전 자동화했을까요?
백엔드 VM 리눅스 커널의 local 라우팅 테이블 실체 확인 (ip route show table local proto 66) 
$ ip route show table local proto 66
local 10.10.99.99 dev ens4 proto 66 scope host    # <-- google-guest-agent가 LB VIP(10.10.99.99)를 내 로컬 IP처럼 자동 주입!
자동화된 DSR 동작 3단계
  • 1. 메타데이터 동기화: MIG가 Passthrough NLB의 백엔드로 연결되면, Andromeda 컨트롤 플레인이 해당 VM의 메타데이터(instance/network-interfaces/0/forwarded-ips)에 LB VIP 주소를 기록합니다.
  • 2. proto 66 로컬 라우트 주입: VM 내부의 google-guest-agent 데몬이 이를 감지하여 커널 local 라우팅 테이블에 proto 66으로 LB VIP를 자동 등록합니다.
  • 3. Direct Server Return 응답: 리눅스 커널은 목적지(`10.10.99.99`)를 자기 자신의 IP로 인식해 애플리케이션 소켓으로 올리고, 응답할 때도 출발지 IP에 10.10.99.99를 찍어 클라이언트에게 직접 반환합니다.
실무 트러블슈팅 주의사항 2가지
  • 주의 1 (커스텀 이미지 데몬 누락): 자체 제작한 이미지에서 google-guest-agent 서비스를 끄거나 삭제하면, proto 66 라우트가 생성되지 않아 Passthrough NLB 헬스 체크가 100% 실패합니다.
  • 주의 2 (Hairpinning 자기 호출 금지): 백엔드 VM 자신이 자기가 속한 Passthrough NLB의 VIP를 호출하면, 패킷이 외부로 나가지 않고 커널 local 테이블에 의해 자기 자신(Loopback)으로 바로 꺾여 들어갑니다.
핵심 요약Passthrough NLB 헬스 체크가 안 붙을 때는 방화벽 확인과 함께 백엔드 VM 안에서 ip route show table local proto 66에 VIP가 떠 있는지 확인하십시오.

3.5 왜 GCP Load Balancer는 5개의 리소스로 조립하도록 설계되었는가?

맥락(Why): 타 클라우드에서는 LB 하나를 만들면 리스너와 타겟 그룹만 있는데, GCP에서는 왜 Forwarding Rule → Target Proxy → URL Map → Backend Service → MIG/NEG로 세분화되어 있을까요?
L7 Application Load Balancer vs L4 Passthrough Network Load Balancer 조립 체인 비교 
[L7 ALB 체인]  Forwarding Rule (VIP+포트) ──▶ Target HTTPS Proxy (TLS 인증서+보안정책) ──▶ URL Map (호스트/경로 분기) ──▶ Backend Service (Cloud Armor/Draining/HC) ──▶ MIG / NEG
[L4 NLB 체인]  Forwarding Rule (VIP+포트) ───────────────────────────────────────────────────────────────────────────▶ Backend Service (세션 어피니티/HC)         ──▶ MIG / NEG
컴포넌트 계층 핵심 역할 및 담당 설정 모듈형 분리 설계가 주는 엔터프라이즈 운영 이점
1. Forwarding Rule 클라이언트가 접속하는 진입점 VIP 주소, 프로토콜, 포트 번호, Network Tier 정의 IPv4 VIP용 Forwarding Rule과 IPv6 VIP용 Forwarding Rule 2개를 만들어 동일한 하나의 Target Proxy에 동시 연결 가능
2. Target Proxy TCP/TLS 세션 종료, Certificate Manager SSL 인증서 매핑, SSL 정책(TLS 1.2/1.3 강제), QUIC(HTTP/3) 활성화 HTTP(80) 프록시와 HTTPS(443) 프록시를 각각 두거나 인증서 교체 시 백엔드 구성을 전혀 건드리지 않고 독립 변경
3. URL Map L7 라우팅 테이블: 호스트명(api.example.com), 경로(/v1/pay), 헤더 기반 분기 및 카나리 가중치 분할 마이크로서비스 수십 개가 단 하나의 글로벌 Anycast VIP와 URL Map을 공유하면서 뒤쪽 Backend Service만 팀별로 분리
4. Backend Service Balancing Mode, Session Affinity, Connection Draining, Keep-alive/응답 타임아웃(기본 30초), Cloud Armor WAF, Health Check 동일 서비스의 서울 리전 MIG와 도쿄 리전 MIG를 하나의 Backend Service에 함께 등록하여 글로벌 자동 페일오버 구현
5. MIG / Zonal NEG 실제 트래픽을 처리하는 GCE VM 그룹(MIG) 또는 컨테이너 파드 IP:Port 엔드포인트(Zonal NEG) VM에서 GKE 컨테이너로 마이그레이션할 때, URL Map이나 Backend Service에서 백엔드만 MIG → NEG로 무중단 스위칭
핵심 요약5단계 컴포넌트 분리는 단일 VIP 아래에서 수십 개의 VM 그룹과 GKE 서비스를 레고 블록처럼 조합하고 무중단 마이그레이션하기 위한 설계입니다.

3.6 전용선(Interconnect)/VPN 환경에서의 Internal LB 연동과 NVA 체이닝

맥락(Why): 온프레미스 데이터센터와 전용선(Dedicated/Partner Interconnect)을 연결하고 BGP 라우팅까지 정상 확인했는데, 왜 온프레미스 서버에서 GCP의 Internal LB VIP를 호출하면 타임아웃이 날까요?
1. 온프레미스 → Internal LB 호출 시 필수 설정
  • 원인: Internal Passthrough NLB와 Internal ALB의 Forwarding Rule은 기본적으로 동일 리전 내의 클라이언트만 접근 허용하도록 잠겨 있습니다.
  • 해결책 (Global Access 활성화): 온프레미스 네트워크나 타 리전 서브넷에서 Internal LB VIP를 호출하려면 반드시 Forwarding Rule에 --allow-global-access 플래그를 켜야 합니다.
  • 하이브리드 역방향(GCP LB → 온프레미스 서버): 반대로 GCP LB 뒤에 온프레미스 서버 IP:Port를 붙여 카나리 이관을 할 때는 Hybrid Connectivity NEG(NON_GCP_PRIVATE_IP_PORT)를 사용합니다.
2. 서드파티 방화벽 어플라이언스(NVA) 무중단 이중화
  • 온프레미스처럼 VRRP(Active-Standby)로 방화벽 VM을 구성하면 페일오버가 느리고 대역폭이 절반으로 낭비됩니다.
  • GCP 표준 아키텍처 (--next-hop-ilb): 멀티 NIC 기반 방화벽 VM들을 Regional MIG(Active-Active)로 묶고, 그 앞에 Internal Passthrough NLB를 배치한 뒤 VPC 커스텀 라우트의 Next Hop을 해당 NLB로 지정합니다.
  • 대칭 해싱(Symmetric Hashing): Andromeda SDN이 오가는 패킷의 5-Tuple을 대칭 해싱하여 항상 동일한 방화벽 VM을 통과하도록 보장하므로 세션 테이블 깨짐이 없습니다.
gcloud CLI · 온프레미스 접근을 허용하는 Internal LB Global Access 활성화 및 Next-Hop ILB 라우트 
# 1. 온프레미스 및 타 리전에서 Internal LB VIP 접근 허용
gcloud compute forwarding-rules update internal-was-fr --region=asia-northeast3 --allow-global-access

# 2. VPC 기본 라우트(0.0.0.0/0)의 Next Hop을 방화벽 MIG 앞단의 Internal Passthrough NLB로 지정
gcloud compute routes create default-via-fw-nlb --network=spoke-vpc --destination-range=0.0.0.0/0 --next-hop-ilb=fw-inspect-nlb

3.7 외부 API 집중 호출 시 Cloud NAT 포트 고갈(OUT_OF_RESOURCES) 해결

맥락(Why): 공인 IP가 없는 Private VM들이 외부 카드사·은행·알림톡 API와 초당 수천 건의 통신을 할 때, VM CPU와 대역폭은 널널한데 간헐적으로 아웃바운드 연결 타임아웃이 발생하는 이유는 무엇일까요?
단일 외부 목적지(IP:Port) 집중 호출 시 Cloud NAT 동시 연결 한계 및 TIME_WAIT 누적 공식 
* NAT 공인 IP 1개당 사용할 수 있는 총 소스 포트 수 = 64,512개 (1,024 ~ 65,535)
* 만약 백엔드 VM들이 동일한 외부 PG사 서버(예: 211.x.x.x:443) 하나에 매 요청마다 새 TCP 연결을 맺고 끊는다면?
  ──▶ 닫힌 소켓도 커널 및 NAT 테이블에서 120초(TIME_WAIT) 동안 포트를 점유!
  ──▶ VM당 기본 정적 할당(64 포트) 사용 시, 해당 VM은 초당 단 0.5건(64 / 120초)만 연결해도 즉시 포트 고갈(OUT_OF_RESOURCES) 발생!
1. Dynamic Port Allocation 활성화
  • 고정 64포트 대신 트래픽이 몰리는 VM에 minPortsPerVm(예: 1024)부터 maxPortsPerVm(예: 16384)까지 포트를 동적으로 즉시 증설합니다.
2. Endpoint-Independent Mapping 해제
  • --no-enable-endpoint-independent-mapping을 확인합니다.
  • 비활성화 시 서로 다른 외부 목적지 IP:Port에 대해서는 동일한 NAT 소스 포트를 재사용(5-Tuple 구분)할 수 있어 포트 효율이 수십 배 높아집니다.
3. 다중 NAT IP 산정 공식 & 연결 풀링
  • 필요 NAT 공인 IP 수 공식:
    ceil( (VM 수 × 최대 포트) / 64,512 )
  • 애플리케이션 코드에서도 외부 API 호출 시 매번 소켓을 닫지 않고 HTTP Keep-Alive 커넥션 풀을 재사용해야 합니다.
핵심 요약외부 연동이 많은 VPC의 Cloud NAT에는 반드시 Dynamic Port Allocation과 충분한 수동 고정 NAT IP 풀을 사전 할당하십시오.

3.8 Balancing Mode(UTILIZATION vs RATE)와 트래픽 쏠림 방지

맥락(Why): Load Balancer의 Backend Service에도 maxUtilization(기본 80%) 설정이 있고, MIG Autoscaler에도 targetCpuUtilization 설정이 있습니다. 이 둘의 관계가 어긋나면 어떤 기현상이 벌어질까요?
잘못된 설계 시나리오: LB maxUtilization(0.8) < MIG Autoscaler CPU 임계치(0.85) 일 때의 부하 전이 
[Zone A의 CPU가 81% 도달] ──▶ MIG Autoscaler는 아직 85%가 안 되었으므로 VM을 늘리지 않고 가만히 있음!
                          ──▶ 반면 LB는 "Zone A 용량(80%)이 꽉 찼다!"고 판단하여 잉여 트래픽을 다른 존/리전으로 우회(Spillover)시킴!
Balancing Mode 선택 기준
  • RATE (초당 요청 수 RPS 기준 · L7 ALB 권장): 인스턴스당 처리 가능한 최대 RPS(예: maxRatePerInstance = 500)를 기준으로 분배합니다. CPU 지연 신호보다 즉각적이고 예측 가능한 분산을 제공합니다.
  • UTILIZATION (백엔드 CPU + 사용률 기준): 요청마다 걸리는 작업 시간 편차가 매우 큰 워크로드에 적합합니다.
  • CONNECTION (동시 연결 수 기준 · L4 Proxy NLB): 장시간 연결을 유지하는 TCP/WebSocket 워크로드에 사용합니다.
Autoscaler 임계치와의 연동 골든 룰
  • 항상 Autoscaler가 LB 상한선보다 먼저 반응해야 합니다!
  • 예: MIG Autoscaler 목표치를 60%~65%로 잡고, Backend Service의 최대 용량 상한(maxUtilization)은 80%로 두어, LB가 트래픽을 다른 곳으로 밀어내기 전에 MIG가 먼저 스케일 아웃되도록 설계합니다.
  • 또한 capacityScaler 파라미터(0.0 ~ 1.0)를 사용하면 특정 백엔드 그룹으로 가는 트래픽 비율을 즉시 줄이거나 차단(0.0)할 수 있습니다.
핵심 요약MIG Autoscaler Target (60%) < LB Max Capacity (80%) 부등식을 항상 유지해야 예기치 않은 교차 존 트래픽 넘침(Spillover)을 막을 수 있습니다.

3.9 간헐적 502 Bad Gateway의 주범: Keep-alive Race Condition과 620초 공식

맥락(Why): 서버 CPU도 10% 미만이고 애플리케이션 에러 로그도 전혀 없는데, 하루에 수십 건씩 간헐적으로 502 Bad Gateway가 발생합니다. 전 세계 클라우드 엔지니어들이 가장 많이 겪는 이 문제의 정확한 원인과 해결 공식은 무엇일까요?
LB 프록시(600초) vs 백엔드 웹서버(기본 5~75초) Keep-alive 불일치로 인한 TCP FIN / HTTP 요청 충돌 과정 
[GFE / Envoy 프록시] ◀──(기존 재사용 유휴 TCP 연결)──▶ [백엔드 Nginx(기본 65초) / Node.js(기본 5초) / Tomcat(기본 20초)]
  1) 유휴 시간이 65초가 되는 순간, 백엔드 웹서버가 스스로 소켓을 닫기 위해 LB 쪽으로 [TCP FIN] 패킷을 전송!
  2) 바로 그 찰나(수 ms 차이), 패킷이 아직 도착하기 전에 LB 프록시는 이 연결이 살아있는 줄 알고 새 고객의 [HTTP POST 요청]을 전송!
  3) 이미 소켓을 닫은 백엔드 커널이 [TCP RST]로 거부 ──▶ LB가 클라이언트에게 502 Bad Gateway 반환! (로그: backend_connection_closed_before_data_sent_to_client)
절대 불변의 방지 공식: 백엔드 Keep-alive = 620초!
  • Google Cloud ALB(GFE 및 Envoy)의 백엔드 유휴 연결(Keep-alive) 타임아웃은 600초(10분)로 고정되어 있습니다.
  • 해결 원리: 항상 백엔드 웹서버가 먼저 연결을 끊지 말고, LB 프록시가 600초에 먼저 안전하게 연결을 정리하도록 백엔드의 Keep-alive 타임아웃을 600초보다 큰 620초로 설정하면 Race Condition이 원천 소멸됩니다.
언어·웹서버별 백엔드 Keep-alive 620초 필수 설정 코드 
# [1. Nginx (nginx.conf)]
keepalive_timeout 620s;
keepalive_requests 100000;   # 기본 1000건 도달 시 조기 종료 방지

# [2. Node.js (Express / Fastify / NestJS)]
server.keepAliveTimeout = 620 * 1000;
server.headersTimeout   = 625 * 1000;  # keepAliveTimeout보다 크게!

# [3. Spring Boot (application.yml) / Go (http.Server)]
server.tomcat.keep-alive-timeout: 620s   # Go: IdleTimeout: 620 * time.Second
Session 3 마무리사내 표준 Golden Image의 Nginx/Tomcat/Node.js 설정에 Keep-alive 620초를 기본 박아두면 간헐적 502 장애를 100% 예방할 수 있습니다.

4.3 502/503/504 에러 발생 시 추측을 끝내는 statusDetails 판독표

맥락(Why): 같은 502 Bad Gateway라도 백엔드 앱이 죽은 건지, 방화벽이 막힌 건지, Keep-alive 타임아웃 충돌인지 어떻게 알 수 있을까요? LB 로그의 jsonPayload.statusDetails에 정확한 정답이 적혀 있습니다.
jsonPayload.statusDetails 값 HTTP 코드 정확한 발생 원인 즉각 조치 플레이북
response_sent_by_backend 정상 / 5xx LB는 정상 전달했으며, 백엔드 애플리케이션 코드 자체가 500/502를 생성해 반환함 LB 이상 없음. 백엔드 애플리케이션 에러 로그(Stack Trace) 확인
backend_connection_closed_before_data_sent_to_client 502 Keep-alive 타임아웃 불일치(Race Condition)로 백엔드가 먼저 TCP FIN/RST를 보냄 Session 3.9 공식 적용: 백엔드 웹서버 Keep-alive를 620초로 상향
failed_to_connect_to_backend 502 LB 프록시가 백엔드 VM과의 TCP 3-way Handshake(SYN) 자체에 실패함 방화벽에서 LB 대역(35.191.0.0/16, 130.211.0.0/22, Proxy-only) 허용 여부 확인
failed_to_pick_backend 502 / 503 현재 트래픽을 받을 수 있는 Healthy 상태의 백엔드 VM이 단 1대도 없음(전멸) LB Health Check 경로/포트 오타 또는 전체 백엔드 다운 여부 즉시 점검
backend_timeout 504 백엔드가 Backend Service의 timeoutSec(기본 30초) 안에 응답을 주지 못함 장시간 API인 경우 timeoutSec을 60~300초로 상향 및 슬로우 쿼리 튜닝
Cloud Logging LQL · 백엔드 자체 에러를 제외하고 순수하게 LB 구간에서 발생한 5xx 에러만 필터링 
resource.type="http_load_balancer" AND httpRequest.status>=500 AND jsonPayload.statusDetails!="response_sent_by_backend"
핵심 요약위 Cloud Logging 쿼리 한 줄을 모니터링 알림에 등록해 두면 백엔드 앱 에러와 인프라 연결 에러를 즉시 분리할 수 있습니다.

4.5 Terraform을 활용한 불변 템플릿 무중단 교체 패턴 & 종합 정리

맥락(Why): Instance Template은 수정이 불가능하여 변경 시 삭제 후 재생성됩니다. 그런데 이미 MIG가 구버전 템플릿을 물고 있으면 Terraform이 resourceInUseByAnotherResource 에러를 뱉으며 멈춥니다. 어떻게 해결할까요?
Terraform MIG 무중단 배포 필수 공식
  • 1. 고정 name 대신 name_prefix 사용: 매 변경 시 고유한 타임스탬프/해시 접미사가 붙은 신규 템플릿이 생성되도록 합니다.
  • 2. create_before_destroy = true 선언: 신규 템플릿을 먼저 생성 → MIG의 version 블록이 신규 템플릿으로 롤링 업데이트 시작 → 참조가 해제된 구버전 템플릿을 마지막에 안전하게 삭제합니다.
  • 3. CLI vs Terraform 역할 분담: 일상적인 형상/인프라 변경은 100% Terraform으로 관리하고, 긴급 장애 시 콘솔/CLI로 우회 조치한 경우 당일 내 코드에 반영해 드리프트를 제거합니다.
Terraform HCL · 종속성 충돌 없는 무중단 롤링 업데이트 표준 코드 
resource "google_compute_instance_template" "was_tpl" {
  name_prefix  = "prod-was-tpl-"   # 1. 고정 name 대신 prefix 사용!
  machine_type = "c3-standard-4"
  # ... (디스크, gVNIC, 이미지 설정) ...

  lifecycle {
    create_before_destroy = true   # 2. 새 템플릿 생성 및 MIG 교체 후 구버전 삭제!
  }
}

resource "google_compute_region_instance_group_manager" "was_mig" {
  name   = "prod-was-mig"
  region = "asia-northeast3"
  version {
    instance_template = google_compute_instance_template.was_tpl.self_link_unique
  }
  update_policy {
    type            = "PROACTIVE"
    minimal_action  = "REPLACE"
    max_surge_fixed = 3            # 3개 존 동시 병렬 Surge
    max_unavailable_fixed = 0      # 용량 100% 유지
  }
}
